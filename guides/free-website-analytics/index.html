Guide · Measurement

Free website analytics without running your own server.

Use one focused tool for visits, one for Google Search, and one for technical quality. The result is clearer than a giant dashboard—and much easier to maintain.

Published August 26, 202612 minute readPrimary-source links included

Start with questions, not dashboards

Website owners often ask for “full analytics” as if every useful number lives in one product. It does not. A visit recorded by a browser, an impression recorded by Google Search, and a simulated mobile performance score describe three different systems.

A small static website can cover the essential questions without renting an analytics server:

  1. Are real people visiting, and which pages or sources bring them? Use Cloudflare Web Analytics.
  2. How often does Google show the site, for which queries, and which pages earn clicks? Use Google Search Console.
  3. Is the page fast, accessible, and technically sound under repeatable test conditions? Use Lighthouse or PageSpeed Insights.

The useful dashboard is the decision routine. Tools collect evidence. A weekly review turns that evidence into a prioritized change.

Layer 1: Cloudflare Web Analytics for visits

Cloudflare describes Web Analytics as free, privacy-first analytics that can report page views, visitors, and real-user performance. Its browser beacon uses the Performance API, and Cloudflare states that the product does not collect or use visitors' personal data.

That makes it a good first layer for a small informational site. It answers questions such as:

  • Which pages receive visits?
  • Which external sites or campaigns send those visits?
  • Which countries and devices appear in aggregate?
  • How do real users experience loading and responsiveness?

How to connect a DNS-only static site

The Renew Up uses Cloudflare for DNS but Netlify for hosting, and its public DNS answers show the Netlify addresses directly. For this type of site, Cloudflare's official setup guide says to add the hostname in Web Analytics, copy the generated JavaScript snippet, and place it before the closing body tag on each page.

  1. Sign in to the Cloudflare account that owns the zone.
  2. Open Web Analytics and add the exact hostname.
  3. Copy the site-specific beacon token or generated snippet.
  4. Add the snippet to the shared page template or each static page.
  5. Deploy once and verify that new visits appear after Cloudflare's processing delay.

Do not invent a token or copy one from another site. A hostname mismatch can produce a CORS error; Cloudflare's Web Analytics FAQ specifically recommends checking that the configured hostname matches the site loading the beacon.

Layer 2: Search Console for Google visibility

Visitor analytics starts after a person reaches the site. Search Console describes what happened before that click. Google's performance-report documentation defines the core search metrics:

  • Impressions: a link to the site was shown in a Google surface under the product's counting rules.
  • Clicks: someone clicked a Google result leading to the site.
  • Click-through rate: clicks divided by impressions.
  • Average position: the average topmost result position, best used as a trend rather than a standalone score.

The most valuable dimensions are often query and page. Query data reveals the language people use. Page data shows which answers Google is willing to surface.

A practical Search Console setup

  1. Create or open the domain property for the exact domain.
  2. Verify ownership through DNS. The Renew Up already has a Google site-verification TXT record, but the correct Google account still must be selected.
  3. Publish a sitemap at a stable HTTPS URL.
  4. Submit that sitemap inside Search Console.
  5. Inspect the homepage and a representative article to confirm the selected canonical URL and indexing status.

Google's SEO Starter Guide is deliberately clear: there is no secret that guarantees a first-place ranking. A sitemap helps search engines discover the URLs you care about; it does not turn low-value pages into winners.

Layer 3: Lighthouse for repeatable technical checks

Lighthouse is a lab test, not a visitor counter. It runs a page under controlled conditions and audits performance, accessibility, best practices, and a subset of SEO requirements.

Use it to catch regressions such as:

  • render-blocking CSS or scripts;
  • slow Largest Contentful Paint;
  • layout shifts;
  • unlabeled controls and insufficient contrast;
  • missing landmarks, titles, or basic crawl directives.

Run the same URL and profile more than once. Compare a median or a trend. A single score can change because of machine load, network conditions, browser version, or third-party resources.

A Lighthouse SEO score of 100 does not mean a page ranks. The original Renew Up homepage scored 100 in that category while having no sitemap, no analytics, one generic page, and no useful search visibility.

The weekly scorecard

A small site does not need a daily command center. A 20-minute weekly review is usually enough at the beginning.

Track behavior without pretending to identify people

“People visiting” should usually mean aggregate audience behavior, not a dossier on an individual. A privacy-first setup can answer which page worked, where traffic came from, and how the site performed without collecting names or trying to identify a visitor.

If the site later adds a newsletter, consultation request, account, or purchase, that is a separate conversion system. It needs a real data destination, clear consent language, a retention policy, and access controls. Do not smuggle personally identifiable information into analytics events.

When Google Analytics becomes useful

GA4 can be appropriate when the site needs detailed event models, campaign attribution, audiences, advertising integrations, or complex conversion funnels. It also brings more configuration and privacy work.

For a new content experiment, Cloudflare plus Search Console can answer the first decisions with less complexity. Add GA4 only after a specific unanswered question justifies it—not because every site is expected to have it.

Do you need a custom dashboard?

Usually not on day one. A custom dashboard still needs data sources, credentials, refresh logic, error handling, and secure access. It can make three imperfect sources look unified without making them more accurate.

Start with direct links to the authoritative dashboards and a public summary page that labels dates and sources. Automate only after the same manual report has proven useful for several cycles.

The Renew Up implementation order

  1. Publish the rebuilt static pages, robots.txt, and sitemap.xml.
  2. Use the confirmed account to enable Cloudflare Web Analytics and insert its site-specific beacon.
  3. Open the verified Search Console property, submit the sitemap, and record the first indexing state.
  4. Run Lighthouse against the production pages after deployment.
  5. Update the public growth dashboard only with those verified production results.

That stack uses the existing delivery architecture. No custom analytics server needs to run on a home computer, and no new production database is required.
