Guide · Hosting

Develop locally. Serve the public site somewhere built to stay online.

Local development saves money and gives control. Static hosting keeps the domain fast, encrypted, and available when the computer sleeps. A small site can—and usually should—use both.

Published August 26, 20269 minute readBased on The Renew Up's real stack

“Local” and “hosted” solve different problems

Local development means the editable website files and a preview server run on your computer. You can work without publishing every experiment, use Git to track changes, and test a new version before anyone else sees it.

Production hosting means a service answers requests for the public domain all day and night. It terminates HTTPS, serves files near visitors, handles traffic spikes, and remains available when your computer is off.

The low-cost setup is not “local instead of hosting.” It is local for building, Git for history, and the existing static host for reliable public delivery.

Why a personal computer is a fragile public server

A home-hosted website can work as a technical project, but it quietly transfers several hosting responsibilities to the owner.

  • Uptime: the site disappears during sleep, restart, power loss, updates, or internet outages.
  • Network reachability: residential connections may use changing IP addresses, carrier-grade NAT, blocked inbound ports, or router rules that require ongoing maintenance.
  • TLS certificates: HTTPS renewal and configuration become the owner's job.
  • Security exposure: opening a device to the public internet expands the attack surface and creates patching and log-monitoring work.
  • Performance: upload bandwidth and geography limit response speed for remote visitors.
  • Operations: backups, observability, denial-of-service resistance, and incident recovery are no longer someone else's platform problem.

Those costs may not appear on a hosting invoice, but they are still real. They are paid in time, risk, electricity, and unavailable pages.

Why static hosting fits this site

The Renew Up is plain HTML and CSS. No server renders the page for each visitor. There is no production database, account system, checkout, or private API. A static host can serve the exact files efficiently.

The existing production site is already on Netlify, and Netlify publicly identifies the GitHub repository and deployed commit. Keeping that path avoids a migration and does not require renting a virtual server for this rebuild.

Static hosting also supports a clean security model: there is no origin application process to compromise, and the deployment can be reproduced from a known Git commit.

The practical workflow

  1. Clone once. Keep the Git repository in a normal local project folder.
  2. Preview locally. For this dependency-free site, a tiny static HTTP server is enough. If the project later uses Netlify-specific functions or redirects, Netlify Dev can reproduce more of the production environment locally.
  3. Work on a branch. Make a focused change without disturbing the last published commit.
  4. Validate locally. Check every internal link, metadata, structured data, sitemap URL, accessibility baseline, and production-like headers.
  5. Commit the exact release. A meaningful message becomes part of the public change history.
  6. Push after review. The connected host can build or publish from Git. Netlify's preview options distinguish local development, deploy previews, branch deploys, and production releases.
  7. Verify production. Confirm the live response, analytics beacon, sitemap, canonical URLs, and a fresh Lighthouse result.

Where money is actually saved

The rebuild stays inexpensive by avoiding machinery the site does not need:

  • no rented virtual private server;
  • no always-on home server;
  • no database for static articles;
  • no JavaScript framework shipped to render straightforward content;
  • no custom analytics backend;
  • no fake admin application pretending browser storage is shared data.

The domain still requires renewal, and any host can impose plan limits or change pricing. The sensible cost control is to keep the architecture portable: standards-based HTML, a Git repository, and no vendor-specific database dependency.

When self-hosting may be justified

Self-hosting can make sense when learning server administration is itself the goal, when data must remain on controlled hardware, when an application needs capabilities the current platform cannot provide, or when a team is prepared to own security and uptime.

Even then, a dedicated machine or managed environment is a different decision from exposing a daily-use personal computer. Define the recovery plan, update process, monitoring, and threat model before pointing a production domain at it.

The Renew Up recommendation

Keep the repository on this computer for development. Keep GitHub as the recoverable source of truth. Keep Netlify as the current public delivery layer while it remains appropriate for the site's traffic and plan. Keep Cloudflare for DNS and, after the correct account is confirmed, privacy-first Web Analytics.

This preserves the best parts of local control without turning a personal computer into critical public infrastructure. It also leaves the site portable: every production page is a file that can move to another static host later.
