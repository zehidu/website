Case study · Day zero

What an untracked website was really hiding.

The homepage looked finished. Underneath it were no real analytics, no sitemap, a lead form that sent nothing, a public demo dashboard, and a clean path to recovery.

Published August 26, 202610 minute readEvidence captured from the live site

The brief

The Renew Up began this audit as a random single-page website with an ambitious goal: become a place where website traffic, search visibility, technical quality, and content growth could be understood without paying for an unnecessary server.

The first job was not redesign. It was control. Before changing a headline or choosing an analytics tool, we needed to answer five basic questions: Who controls the domain? Where does DNS live? Who serves the page? Where is the source code? What, if anything, is already measuring users and Google Search?

Day-zero principle: do not build a growth plan on top of infrastructure you cannot identify or measurements you cannot verify.

The ownership map

Public infrastructure records and the deployment metadata produced a complete map:

  • Registrar: GoDaddy. The domain is registered through September 24, 2027 and carries registry locks that help prevent unauthorized deletion, transfer, or updates.
  • DNS: Cloudflare. The authoritative nameservers are in Cloudflare, and the zone already contains a Google site-verification TXT record.
  • Production hosting: Netlify. The custom domain points to the Netlify site named zesty-custard-83b123.
  • Source of truth: the public GitHub repository zehidu/website, branch main.
  • Deployment: Netlify reports the published Git commit as 0d32206, matching the repository head captured during the audit.

That map matters because it rules out a costly rewrite or an unnecessary hosting migration. The site is a tiny static project. It can be edited and tested locally, stored in Git, and delivered through the existing static host.

The measurement gap

The live HTML contained no Google Analytics tag, Cloudflare Web Analytics beacon, Plausible script, Fathom script, PostHog client, Hotjar tag, Microsoft Clarity tag, or equivalent visitor measurement code. Search Console ownership may exist because the DNS token is present, but private performance data cannot be assumed from a public verification record.

Public search checks also returned no useful indexed result for the domain. That is not surprising. The site had only one generic page, no sitemap, no robots.txt, and no content designed to answer a specific search question.

The form that never reached the owner

The largest functional problem was the contact form. A visitor could enter a name and work email, press the button, and see a confident success message promising a response within 24 hours.

But the form made no network request. Its JavaScript placed the submission into localStorage, a private storage area inside that visitor's own browser. The site owner could not see it from another computer. Netlify received no form submission. No email was sent. No database record was created.

Impact: the form created the appearance of conversion while discarding the business value of every submission. The rebuild removes that false promise. A real form should return only after there is a real destination, consent language, and owner workflow.

The public “admin” was a demo, not a backend

The repository also contained an admin login, dashboard, pipeline, proposals, invoices, and analytics screens. They looked like a small CRM, but every record was invented demo data stored in the browser. There was no shared server-side database and no connection to website traffic.

Worse, the login email and password were hard-coded in the public HTML and JavaScript. Anyone reading the source could recover them. The password-change screen displayed success without changing the actual password. This did not expose a real backend—there was none—but it was still misleading and unsafe to keep.

The local rebuild removes the admin files. Real measurement belongs in Cloudflare and Search Console until there is a genuine need for a private application with server-side authentication.

The technical quality baseline

A Lighthouse 13.4.1 run against the live homepage produced the following simulated mobile baseline:

  • Performance: 87. First Contentful Paint was 3.0 seconds, Largest Contentful Paint was 3.0 seconds, and Speed Index was 4.6 seconds.
  • Accessibility: 71. Automated failures included unnamed buttons, insufficient color contrast, an unlabeled select, skipped heading order, and no main landmark.
  • Best Practices: 96. The page logged browser console errors.
  • Lighthouse SEO: 100. This is a useful reminder that a perfect automated SEO checklist is not the same as being useful, indexed, or ranked.

The biggest performance opportunity was render-blocking external resources: runtime Tailwind CSS and a Google Fonts stylesheet. The new static build uses a local stylesheet and the system font stack, removing those dependencies from the critical path.

Why the old content could not sustain organic growth

The page presented an automation company called AutoFlow. It claimed more than 300 customers, named client brands, quoted testimonials, promised setup in 48 hours, and advertised average savings. None of those claims had supporting evidence in the repository or public site.

Even if the claims had been true, the page still had almost no search surface. It offered one broad commercial pitch instead of a network of pages that answered specific questions. A search engine cannot send many different kinds of intent to a site that has only one generic answer.

The new direction is narrower and verifiable: document this real rebuild. The first content cluster covers the audit itself, a zero-server analytics stack, and the difference between local development and reliable static hosting. Every article links to the public evidence or an authoritative primary source.

Why the home computer is for development, not production

Hosting the public domain directly from a personal computer may sound cheaper, but it introduces uptime, security, TLS, power, residential-network, and maintenance risks. The existing site is static and already served from Netlify's edge. No new rented server is required for this rebuild.

The cost-conscious workflow is straightforward: edit and preview on the computer, commit the exact source to GitHub, and let the existing static host serve the production copy. The local-versus-static hosting guide explains the tradeoff in detail.

The first 90 days

  1. Recover and secure. Remove the public demo admin, stop making unsupported claims, replace the false form, publish security headers, and document the actual owners of each layer.
  2. Measure. Connect the correct Cloudflare account, enable Web Analytics, inspect the Search Console property, submit the sitemap, and record the first verified numbers.
  3. Publish a tight topic cluster. Build pages around measurement, technical SEO, static-site operations, accessibility, performance, and transparent growth experiments.
  4. Use demand to choose the next page. After impressions appear, improve titles and answers for queries with clear intent instead of guessing at a large editorial calendar.
  5. Keep a changelog. Date every material release and compare periods inside Search Console so apparent improvements have context.

That is the day-zero result: not a promise of overnight rankings, but control of the stack, an honest baseline, a credible subject, and a measurement plan capable of proving whether the work helps.
